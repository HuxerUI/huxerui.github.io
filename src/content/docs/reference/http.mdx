Declared by `<huxerui/http.h>`.

## Request and response values

- `HttpMethod`: `Get`, `Head`, `Post`, `Put`, `Patch`, `Delete`, `Options`.
- `HttpHeader`: name and value.
- `HttpRequest`: URL, method (default GET), headers, body, and optional timeout (default 30 seconds; `nullopt` disables it).
- `HttpResponse`: final URL, integer status code, headers, and body.

## Errors and result

`HttpErrorCode` is `Transport`, `Timeout`, or `Unsupported`. `HttpError` contains code and message. `HttpResult` constructs from response/error, reports `HasResponse`, and provides ref-qualified `Response()` plus lvalue `Error()` accessors; asking for the wrong alternative throws.

## `HttpClient`

Non-copyable root service. `Send(HttpRequest) const -> Task<HttpResult>`. Obtain it with `UseService<HttpClient>()`. Request cancellation follows the launched HuxerUI task execution.

## Complete request example

```cpp compile="http-request"
#include <huxerui/huxerui.h>

using namespace huxerui;

Task<void> LoadStatus(std::shared_ptr<HttpClient> http, State<std::string> output) {
  HttpResult result = co_await http->Send({
      .url = "https://example.com/status",
      .method = HttpMethod::Get,
  });
  output = result.HasResponse() ? std::to_string(result.Response().status_code) : result.Error().message;
}

[[huxerui::composable]]
View LoadStatusButton(State<std::string> output) {
  auto http = UseService<HttpClient>();
  auto tasks = UseTaskScope();
  return Button("Load status").OnClick([http, tasks, output] {
    tasks.Launch(LoadStatus(http, output));
  });
}
```

Resolve `HttpClient` and `TaskScope` during composition, then capture them in the event.
HTTP status codes are responses; transport, timeout, and unsupported-service failures use `HttpError`.

## Streaming and progress

`Send(request, progress = {})` buffers the full response. `SendStream(request, progress = {})` returns `Task<HttpStreamResult>` after final headers, before body completion. Both progress callbacks and task continuations run on the owning UI thread; do not wrap HTTP in `RunWorker` or post its continuation again.

`HttpProgress` carries `kind` (Upload or Download), `transferred_bytes`, and optional `total_bytes`. A missing total is unknown, not zero; avoid inventing a percentage for compressed or otherwise ambiguous content.

`HttpResponseStream` is move-only and owns the operation. `Url()`, `StatusCode()`, and `Headers()` inspect final response metadata. `Read()` produces `HttpStreamReadResult`: exactly one of `HasData()`, `IsComplete()`, and `HasError()` is true. Only one read may be pending. Reading after EOF/error/cancellation or using a moved-from stream is a logic error; destroying an unfinished stream cancels it.

```cpp compile="http-stream"
#include <huxerui/huxerui.h>

#include <cstddef>
#include <memory>
#include <string>

using namespace huxerui;

Task<void> CountResponse(std::shared_ptr<HttpClient> http, State<std::string> status) {
  auto opened = co_await http->SendStream({.url = "https://example.com/data"});
  if (!opened.HasResponse()) {
    status = opened.Error().message;
    co_return;
  }
  auto& stream = opened.Response();
  if (stream.StatusCode() < 200 || stream.StatusCode() >= 300) {
    status = "Unexpected HTTP status";
    co_return;
  }
  std::size_t received = 0;
  while (true) {
    auto read = co_await stream.Read();
    if (read.HasData()) {
      received += read.Data().size();
      status = std::to_string(received) + " bytes";
    } else if (read.HasError()) {
      status = read.Error().message;
      co_return;
    } else {
      status = "Complete: " + std::to_string(received) + " bytes";
      co_return;
    }
  }
}
```

Launch this task from an event through `TaskScope`. Keeping `opened` alive keeps its referenced stream alive, so no ownership transfer is needed. Chunks are 1 byte through 64 KiB and do not preserve UTF-8, JSON, or record boundaries. Decode incrementally or collect bytes under an application size limit. Browser requests remain subject to CORS and server policy.

## Validate requests and classify outcomes

HttpClient validates a declaration synchronously before returning a Task. The URL must be absolute HTTP/HTTPS; GET and HEAD must not carry a body. Header names must be valid nonempty HTTP tokens, and values must not contain NUL, CR, or LF. A specified timeout must be positive. These are caller errors, not `HttpErrorCode::Transport` results to retry unchanged.

| Outcome | Application handling |
| --- | --- |
| `HasResponse()` with expected 2xx status | Consume/decode the body under application limits. |
| Response with 4xx/5xx status | Handle protocol/application failure; a response is not necessarily success. |
| `HttpErrorCode::Transport` | Connection, TLS, loading, or protocol failure before the requested result. |
| `HttpErrorCode::Timeout` | The complete operation exceeded its deadline. |
| `HttpErrorCode::Unsupported` | The adapter cannot provide this capability; choose a feature fallback. |
| Task cancellation | No normal completion or cancellation exception; the task owner updates UI policy. |

`timeout` covers redirects and streamed body consumption, not just opening the connection. Setting it to `std::nullopt` removes HuxerUI's deadline, not platform or network failures. The final response URL can differ after redirects; do not assume it is the original origin when applying application policy.

## Body and progress ownership

HttpRequest owns a `Bytes` body; encode JSON or form data and supply the corresponding Content-Type yourself. Buffered response bodies occupy memory until released. Choose `SendStream` for large/unknown bodies, enforce an application byte limit, and stop reading when the response is not useful. Destroying the unfinished stream cancels its remaining work.

Progress callbacks run on the UI thread. Keep them short, update only meaningful UI state, and do not perform synchronous disk writes in them. `total_bytes` is optional; transferred bytes are useful even when a percentage is not. Never infer a completed document from a progress value alone—wait for the buffered result or stream EOF.

Retries, authentication refresh, response parsing, and caching belong to application policy. Retry only operations safe to repeat; cancellation or a transport failure does not prove that a POST had no effect. Do not wrap HTTP in a worker or add a second callback-dispatch layer around its Task continuation.
