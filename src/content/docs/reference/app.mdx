## Application declaration

`RootFactory` is `View (*)()`. `Application(root_factory, AppOptions = {})` retains the immutable declaration used by RunApplication. The declaration must outlive the application Runtime. A window's root already owns a composition scope; do not annotate the app root.

| AppOptions field | Contract |
| --- | --- |
| `window` | WindowOptions for the initial window. |
| `viewport_breakpoints` | Width thresholds for responsive composition. |
| `show_debug_overlay` | Defaults on in debug builds and off in release builds; applies to each UI window. |
| `quit_on_last_window_closed` | Defaults true for framework-owned desktop windows. Hidden windows still count; an initially windowless application does not immediately quit. |
| `application_hooks` | ApplicationHook callbacks installed once, in declaration order, before windows or queued application work. |
| `window_hooks` | WindowHook callbacks installed before each UiWindow first composes. |

RunApplication enters the platform shell. Creating an Application value alone does not create a window or start an event loop.

## ApplicationContext and ApplicationHook

An ApplicationHook receives a borrowed ApplicationContext on the application thread. Do not retain it. `Provide<Service>(shared_ptr<Service>)` installs a non-null service under its exact C++ type. Duplicate types and installation after freeze throw logic_error.

`RegisterPlatformModule<Module>(name, factory)` and its options overload install lazy factories accepting Runtime& or UiWindow&. `RegisterPlatformView<Properties[, Controller]>` installs factories prepared for their actual mounting window. The catalog freezes after application installation; registration does not construct a module or platform view.

`OnActivation(function<void(ApplicationActivation)>)` installs the single application-level activation policy. `OnLifecycleChanged(function<void(ApplicationLifecycleState)>)` installs an application-lifetime observer. These handlers can work without a composed window. See [Lifecycle and activation](/docs/guides/lifecycle-and-activation/) for startup handling and queued delivery.

## WindowContext and WindowHook

A WindowHook receives a borrowed WindowContext for one UiWindow. `Provide<Service>` installs a window-local service; `Layers()` borrows its LayerController. A service type cannot be installed both at application and window scope. Factory registration belongs to ApplicationContext.

Use a window service for presentation coordination or per-window editor policy. Use an application service for a shared document model, networking client, or a capability needed while no window is attached.

## UseService and UseApplication

`UseService<Service>()` returns the installed shared_ptr for the exact type or throws logic_error. It finds application services first, then services from the current window Environment. It does not construct missing services or search derived types.

Frozen application services can be acquired without composition, including from another thread without a window execution context. That does not make their methods or State thread-safe. Window services require their original live window context.

`UseApplication() -> ApplicationHandle` works in application hooks, ordinary application-thread callbacks, events, tasks and composition. A captured handle keeps access to its original application service, not a replacement Runtime after shutdown. Calling without a valid application context or from the wrong thread throws logic_error.

## Activation and lifecycle

`ApplicationActivation` is LaunchActivation, UrlActivation, FileActivation, or NotificationActivation. `StartupActivation()` returns `const optional<ApplicationActivation>&`: background-only startup may have no initial activation. Later input does not replace that value.

`LifecycleState()` observes aggregate Active, Inactive or Background state. `OnLifecycleChanged(handler, dependencies...)` observes distinct transitions while the declaring composition Lifecycle is mounted and does not replay the initial state. Use ApplicationContext observers when the policy must outlive every window. WindowHandle has a separate WindowLifecycleState and observer.

## Create and control windows

`SupportsMultipleWindows()` queries programmatic top-level window support. `OpenWindow(ViewFactory, WindowOptions = {})` creates and presents a separately composed window sharing application services and State. Call it on the original application thread, outside composition and installation.

The factory executes later with a fresh root Environment. Options and local theme/locale do not inherit from the caller. Copy required values into the factory; captured references do not gain ownership. Discarding the WindowHandle leaves the window open. Success does not guarantee the first frame has rendered.

Invalid configuration throws invalid_argument, invalid thread/lifetime throws logic_error, and unsupported or failed native creation throws runtime_error. `Quit()` requests whole-application termination; `WindowHandle::Close()` requests only that window's close path.

## Permission requests

Permission covers Camera and Microphone. CheckPermissionAsync and RequestPermissionAsync return Task of PermissionStatus. States are NotDetermined, Granted, Denied, PermanentlyDenied, Restricted, Unavailable and Provisional; notifications use their separate authorization methods and can report Provisional.

```cpp compile="application-permission"
#include <huxerui/huxerui.h>

using namespace huxerui;

[[huxerui::composable]]
View EnableCamera() {
  auto application = UseApplication();
  auto tasks = UseTaskScope();
  auto status = UseState(PermissionStatus::NotDetermined);
  const PermissionStatus authorization = status;
  return Column {
    Text(authorization == PermissionStatus::Granted ? "Camera allowed" : "Camera not enabled"),
    Button("Enable camera").OnClick([application, tasks, status] {
      tasks.Launch([application, status]() -> Task<void> {
        status = co_await application.RequestPermissionAsync(Permission::Camera);
      });
    }),
  };
}
```

Request/settings methods capture the original native presentation endpoint when called. An expired endpoint does not borrow a replacement window. Some hosts can present without a UiWindow; unavailable hosts return Unavailable. Required Android manifests and Apple usage descriptions remain application configuration.

OpenPermissionSettingsAsync returns whether opening settings was accepted, not whether permission was granted. Recheck on return.

## Clipboard and directories

Clipboard returns the same non-null `shared_ptr<Clipboard>` each time. Query IsAvailable and inspect each operation's result. Methods run synchronously on the application thread; retained clipboard objects report unavailable after shutdown.

```cpp compile="application-clipboard"
#include <huxerui/huxerui.h>

using namespace huxerui;

View CopyTitle(std::string title) {
  auto clipboard = UseApplication().Clipboard();
  return Button("Copy title").With(Enabled(clipboard->IsAvailable())).OnClick([clipboard, title] {
    clipboard->WriteText(title);
  });
}
```

Directories returns a borrowed AppDirectories captured at initialization; copy File values for independent ownership. Unavailable directories throw logic_error. CurrentDirectory queries the process working directory and throws runtime_error on failure. Captured directory values remain usable as paths after Runtime shutdown; paths do not grant filesystem access.

## Notifications and tray

LocalNotifications returns an application service handle without capturing a composition Environment. Text resolution follows the resource context of each submission. See [System capabilities](/docs/reference/system/) and [Local notifications](/docs/guides/local-notifications/).

SystemTray returns the shared application tray handle without requiring composition. Show replaces the shared presentation; Hide removes it. OnActivate installs one committed application handler, normally in an ApplicationHook. There is no dependency-list overload. Keep callbacks application-owned and use an explicit Quit action for a tray-only workflow.

## Platform implementation boundary

Runtime owns application services, ordinary timers, dispatch and the frozen factory catalog. UiWindow owns composition, retained nodes, layout, input, semantics, animation, layers and RenderScene generation. Each platform derives these bases to implement genuine native operations. These are host implementation contracts, not objects an ordinary component constructs or subclasses.

ProcessMetrics contains cumulative CPU time, memory footprint and processor count. Shared application and UI work uses one application thread. See [extension points](/docs/guides/extensions/) before choosing a lower-level integration boundary.
