title: CLI reference
description: Create, diagnose, build, run, and package HuxerUI projects from one platform-aware command line.
---

The `huxerui` CLI owns project generation and platform workflows.
It discovers the SDK, validates the current host, and delegates each build to the platform shell generated with the project.

## Command map

```text
huxerui create app <name> [--build cmake|mcpp] [--template <name>] [--id <project-id>] [-p|--platform <platform-list>]
huxerui create library <name> [--build cmake|mcpp] [--template <name>] [--namespace <cpp-namespace>] [--target <public-cmake-target>] [-p|--platform <platform-list>]
huxerui platform add <platform-list>
huxerui doctor [platform-list]
huxerui setup <platform-list> [--yes]
huxerui devices [platform]
huxerui build [platform-list] [build-options]
huxerui run <platform> [build-options]
huxerui package <platform-list> [build-options]
huxerui open ios
huxerui update [--check] [--version <version>] [--yes]
huxerui mcpp build [--source <path>] [--release] [--locked] [--offline] [--verbose]
huxerui --version
```

A platform list is either a comma-separated list such as `windows,web` or the single value `all`.
Commands still enforce host availability: a Windows host cannot build an iOS application, for example.

## Create projects

Create an application with a reverse-DNS project identifier and selected platform shells:

```bash
huxerui create app notes --id dev.example.notes --platform windows,android,web
```

Create a reusable component library with the same shared-source model:

```bash
huxerui create library rich_text --namespace rich_text --target RichText::RichText --platform windows,android
```

Generated projects keep shared C++ under `src/`, resources under `resources/`, and host-specific integration under `platform/<id>/`.
The CLI scans the shared source tree; adding a source file does not require a second list in every platform shell.

Add a platform later without replacing application-owned files:

```bash
huxerui platform add ios
```

## Choose the build system

Create defaults to CMake. --build mcpp renders a desktop module project; --template selects app, navigation or library package templates. The mcpp path rejects --platform because it has no Android/iOS/Web platform shells.

```bash
huxerui create app notes --build mcpp --template navigation
cd notes
mcpp build
mcpp run
```

Use the [C++ Modules and mcpp guide](/docs/tooling/cpp-modules-and-mcpp/) for source layout, language mode, resources and library consumption. The CMake project layout above applies to the default build path.

## Diagnose and set up tools

`doctor` is read-only.
It reports the selected HuxerUI SDK, external tools, host restrictions, and project integration problems:

```bash
huxerui doctor
huxerui doctor android,web
```

`setup` performs supported prerequisite installation or configuration.
Without `--yes`, it describes each planned action and asks before changing the machine:

```bash
huxerui setup android,web
huxerui setup web --yes
```

The SDK is resolved from `HUXERUI_HOME` first, then relative to the running CLI executable.
Use an explicit environment variable when testing a source checkout or keeping multiple SDK versions.

## Select devices

List all device-capable platforms available on the current host, or select one platform:

```bash
huxerui devices
huxerui devices android
```

If exactly one ready device is present, `run` selects it automatically.
When several devices are ready, pass the stable identifier shown by `devices`:

```bash
huxerui run android --device emulator-5554
```

## Build and run

`build` accepts one or more enabled platforms and defaults to the current host platform when it is part of the project:

```bash
huxerui build
huxerui build windows,web --profile release
```

`run` accepts exactly one platform because it launches one application instance:

```bash
huxerui run windows
huxerui run web --profile release
```

Windows selects an MSVC-compatible generator automatically; `--generator` is intended for other supported CMake workflows.
Android and iOS builds are driven through their platform projects rather than a generic desktop generator.

The shared build options are `--device <id>`, `--profile debug|release`, `--generator <name>`, `--source <checkout>`, `--abi <abi-list>`, `--optimization default|size|minsize`, and `--lto on|off`. Platform drivers validate the options they can use.

## Select target ABIs

`--abi` accepts a comma-separated list when the invocation targets one platform. The CLI normalizes aliases and removes duplicates. Omit it to use the platform and project defaults.

| Platform | ABI selection |
| --- | --- |
| Android | `arm64-v8a` and `x86_64` in one APK. Termux supports only `arm64-v8a`. |
| Windows | `x86_64`. |
| Linux | `aarch64` or `x86_64`. Packaging both publishes separate artifacts in `dist/linux/<abi>`. Run accepts one ABI. A non-host build needs `--source` and a target `CMAKE_TOOLCHAIN_FILE`. |
| macOS | `arm64` or `x86_64`. A universal build needs `--source` and universal dependencies. |
| iOS | `arm64` on devices. A simulator can select `arm64` or `x86_64` as supported by Xcode. |
| Web | `wasm32`. |

`x64` and `amd64` select `x86_64`. `arm64` and `aarch64` normalize to the platform's ARM spelling. For example, `huxerui package android --abi arm64` produces an ARM64 APK.

## Tune release size

`--optimization size` selects the toolchain's size optimization and `minsize` requires `-Oz` support. `--lto on` enables link-time optimization when supported. Both affect release configurations of source targets. Use `--source` to rebuild the framework with these choices. An installed SDK library keeps its published optimization settings.

```bash
huxerui build web --profile release --optimization minsize --lto on
huxerui package android --abi arm64 --source ../HuxerUI --optimization size --lto on
```

See [CMake build options](/docs/tooling/cmake/#release-optimization) for direct builds.

## Package artifacts

`package` builds first and then replaces `dist/<platform>` with the platform driver's distributable artifacts.
Its default profile is `release`:

```bash
huxerui package windows,web
huxerui package android --device emulator-5554 --profile debug
```

Packaging is not code signing or store submission.
The produced files are the input to the platform's signing, notarization, store, or deployment workflow.

Linux AppImage packaging requires `appimagetool`, `patchelf` 0.19.0 or later, and binutils. Generated Android projects use a development signing configuration by default. Supply your own release signing configuration before publishing the APK.

## Open the iOS project

Generate the current library integration and open the Xcode project from a macOS host:

```bash
huxerui open ios
```

Use Xcode for signing, capabilities, device provisioning, and archive distribution; keep shared source and library ownership in the HuxerUI project.

## Update an installed SDK

```bash
huxerui update --check
huxerui update
huxerui update --version 0.2.0 --yes
```

The update command operates on an installed SDK, not a source checkout. --check inspects availability without installing; --version selects a release and --yes skips confirmation. Without --version it resolves the current release. Keep active builds and tools out of the destination during replacement.

On Windows the running CLI cannot replace itself directly: it starts an update worker and prints an update.log location. A successful initial exit means handoff, not completed installation. Inspect that log and rerun --version after the worker finishes. Handled publication failures restore the old SDK, but abrupt termination is not an atomic-update guarantee.

## Standalone mcpp builds

```bash
huxerui mcpp build --source path/to/project --release --locked
```

This is a direct frontend for an installed mcpp executable and a project containing mcpp.toml. It forwards --release, --locked, --offline and --verbose to mcpp build in that directory. It does not generate platform shells, translate huxerui.toml, install mcpp, or run the CMake application workflow.

The [module examples](https://github.com/HuxerUI/HuxerUI/tree/d9f0822f2d33855954083f87bd071d6ac709a9d0/mcpp/examples) demonstrate the supported module build rules, composable transformation, resources and library consumption. This command forwards an existing mcpp project build; project generation and normal use are covered by [C++ Modules and mcpp](/docs/tooling/cpp-modules-and-mcpp/).

## Exit behavior

Usage errors return exit code `2` and print the command synopsis hint.
Environment, build, or platform failures return exit code `1`.
A successful command returns `0`, making the CLI suitable for scripts and CI without parsing human-readable status text.
