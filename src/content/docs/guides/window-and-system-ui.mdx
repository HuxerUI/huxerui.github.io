`WindowOptions` is stable for one UiWindow.
It sets title, initial logical size, content mode, chrome mode, preferred custom title-bar height, and caption labels.

## Choose the root content mode

`WindowContentMode::SafeArea` keeps root content inside platform obstructions. `EdgeToEdge` gives the app the complete drawing surface; apply `SafeAreaPadding` only where content must avoid selected edges.

```cpp fragment
return Content().With(
    SafeAreaPadding{.top = true, .right = true, .bottom = true, .left = true},
    SystemBarsAppearance{
        .status_bar_background = theme.colors.primary,
        .status_bar_content = SystemBarContentBrightness::Light,
    }
);
```

In `SafeArea` mode UiWindow consumes physical safe-area insets before measuring the root.
In `EdgeToEdge` mode the root receives the complete viewport and can apply selected insets to individual surfaces instead of padding the entire application.

Software-keyboard viewport changes are distinct from persistent safe-area insets.

Choose the mode once from product intent.
Use `SafeArea` for conventional document and form surfaces that never draw behind system UI.
Use `EdgeToEdge` when a background, image, map, or shell should reach the physical edge, then apply `SafeAreaPadding` to the specific controls and readable content that must remain unobstructed.
Do not add manual status-bar constants; consume the adapter-provided inset in logical units.

## Style system bars

`SystemBarsAppearance` sets available status-bar and navigation-bar backgrounds and chooses automatic, light, or dark system content.
Use automatic brightness when the adapter can infer it from the resolved background; set an explicit value when the application owns a contrasting surface.

System bar availability varies by mobile platform and window mode.
Unsupported fields remain platform-neutral intent rather than emulated desktop bars.

System-bar appearance is declarative and follows the mounted surface that supplies it.
Keep background and content brightness in the same modifier so a theme or route change cannot briefly produce unreadable system icons.
Automatic brightness is a convenience, not an accessibility guarantee; verify contrast on the actual system-bar treatment used by each mobile platform.

## Use system or custom desktop chrome

Desktop windows default to `WindowChromeMode::System`. `Custom` lets application UI occupy the title-bar surface; compose [WindowTitleBar](../../components/window-title-bar/) and use `UseWindow()` for window commands.

`WindowTitleBar` separates draggable and interactive regions while caption controls invoke the same `WindowHandle` commands as application controls.
Custom caption height comes from `WindowOptions`; choose it to match the application's shell rather than assuming one system height.

Custom chrome makes the entire top surface application UI.
Mark only non-interactive drag regions, keep buttons and text fields outside those regions, and provide localized `WindowCaptionLabels` for the built-in caption actions.
Window commands are requests to the current platform window; an embedded host may not support every operation.

Test custom chrome at normal and maximized sizes, multiple DPI values, all resize edges, keyboard focus, double-click maximize, and screen-reader navigation.
macOS traffic-light geometry and Linux window-manager behavior are not Windows caption geometry, so keep platform reservations in `WindowTitleBarMetrics` rather than hard-coded layout constants.

## Read current metrics

`WindowMetrics` is an environment value containing viewport, remaining safe-area insets, and optional title-bar metrics. System-bar brightness can be automatic, light, or dark. Availability and native behavior vary by platform; see the platform guides.

Responsive composition should normally use `UseViewportClass()`.
Read complete metrics only when geometry such as an edge surface or custom title bar genuinely depends on the exact viewport or remaining insets.

## React to the software keyboard

The platform may reduce the viewport when the input method appears.
That is a window-metrics change, not a new safe-area edge and not a reason to permanently pad the root.
Scrollable text-editing surfaces should let HuxerUI bring the active caret into view while preserving user-driven scroll behavior.

Validate focused fields near every edge, keyboard dismissal, orientation/resize, and transitions between hardware and software keyboards on the target device.

See the [Window API](../../reference/window/) and the relevant [platform guide](../../platforms/).

## Control keyboard visibility

Use a Manual policy when focusing an editor should not immediately summon the keyboard. Requests affect the focused editing session; they do not transfer focus to another field:

```cpp compile="manual-keyboard"
#include <huxerui/huxerui.h>

using namespace huxerui;

[[huxerui::composable]]
View KeyboardControls() {
  auto value = UseState(TextEditingValue::FromText(""));
  auto window = UseWindow();
  return Column {
    TextField(value)
        .InputConfiguration({.keyboard_policy = SoftwareKeyboardPolicy::Manual})
        .OnChanged([value](TextEditingValue next) { value = next; }),
    Button("Show keyboard").OnClick([window] { window.ShowKeyboard(); }),
    Button("Hide keyboard").OnClick([window] { window.HideKeyboard(); }),
  }.With(Spacing(12.0F), Padding(16.0F));
}
```

Focus the editor before requesting ShowKeyboard. HideKeyboard preserves its focus, selection and composition session; it is distinct from clearing focus. Automatic policy also requests the keyboard on session start and a confirmed tap on an already-focused editor. Hardware keyboards and desktop hosts may make these requests visually ineffective.

## Close policy and system tray

`WindowHandle::Show()`, `Hide()`, and `Activate()` control window visibility separately from application lifetime. `OnCloseRequest` and `OnMinimizeRequest` install lifecycle-bound decision handlers: true consumes the request, false lets the platform continue. Do not implement “minimize to tray” unless a usable tray presentation is available.

```cpp compile="system-tray"
#include <huxerui/huxerui.h>
#include <memory>
#include <optional>

using namespace huxerui;

struct TrayModel {
  State<std::optional<WindowHandle>> window{std::optional<WindowHandle>{}};
};

void InstallTray(ApplicationContext& context) {
  auto model = std::make_shared<TrayModel>();
  auto application = UseApplication();
  auto tray = application.SystemTray();
  context.Provide(model);
  tray.OnActivate([model] {
    const std::optional<WindowHandle>& window = model->window;
    if (window && window->IsOpen()) {
      window->Activate();
    }
  });
}

[[huxerui::composable]]
View TrayShell(ImageResource icon) {
  auto model = UseService<TrayModel>();
  auto application = UseApplication();
  auto window = UseWindow();
  auto tray = application.SystemTray();
  Lifecycle([model, window] { model->window = std::optional<WindowHandle>{window}; });
  window.OnCloseRequest([window, tray] {
    if (!tray.IsAvailable()) {
      return false;
    }
    window.Hide();
    return true;
  });
  Lifecycle([application, tray, icon] {
    tray.Show(icon, {
        .tooltip = "Document workspace",
        .menu = {MenuItem("Quit", [application] { application.Quit(); })},
    });
  }, icon);
  return Text("Workspace");
}
```

InstallTray belongs in application_hooks; TrayShell is used by the application's single main window with a packaged raster icon. The activation handler is application-owned and installed once, while the model points to that window. In a multi-window product, choose which window to activate in application policy.

The tray presentation is shared across the application. A component cleanup should not hide a presentation that may have been replaced elsewhere. Explicitly hide it when application policy no longer needs it, or let application shutdown retire it. Keep an explicit Quit action available.

Tray availability depends on the host, especially Linux desktop status-item support. Mobile and browser applications need a normal in-app entry point instead. `WindowOptions::minimum_size` requests a desktop minimum client size; it does not clamp actual WindowMetrics or pretend a mobile viewport is larger.
